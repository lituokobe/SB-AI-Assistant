# Project Guide: SB AI Assistant

## Product Vision
This prototype aims to solve two problems in the current AI assistant:
1. Overly broad information: Users get a wall of links instead of a scoped, curated list.
2. No continuity: The assistant forgets the user's preferences/chat history across sessions.

## Core User Flows to Demonstrate (The "Happy Paths")

> **Step 0 (all flows):** Before routing begins, the context window is assembled from the user profile, the session summary, and the last 3 conversations. This is the "harness engineering" approach — it shapes every response implicitly.

### Digital Product
1. **[context]** Context window assembled (profile + summary + last 3 conversations).
2. User types: "I need a phone with a good camera."
3. `router` node identifies intent as "digital".
4. `scoping` node checks profile — no brand preference yet, so it generates Quick-Tap buttons: [Look for a Brand], [Compare Models], [Find Max Cashback].
5. User clicks [Find Max Cashback].
6. `search` node fetches mock products with the highest cashback percentages.
7. `guardrail` node filters out non-phone items (e.g., TVs, accessories).
8. `response` node generates the final recommendation text (mocked LLM, tone shaped by profile).
9. `profile` node implicitly updates the user profile (e.g., adds "Interests: Smartphones", "Prioritises: Cashback").
10. UI renders the chat response and the updated sidebar profile.

### Travel Product
1. **[context]** Context window assembled.
2. User types: "I want to book a trip to Sydney."
3. `router` node identifies intent as "travel".
4. `scoping` node (round 1) generates Quick-Tap buttons: [Family Trip], [Business Trip], [Leisure Trip].
5. User clicks [Business Trip].
6. `scoping` node (round 2) generates text fields: [travel group size], [starting date], [end date].
7. User inputs 2, 2026-08-10, 2026-08-13.
8. `search` node fetches flights/hotel combinations from different platforms (e.g. Trip.com, Booking.com, Agoda) with different cashback percentages.
9. `guardrail` node filters out results that don't meet requirements (e.g. hotels not suitable for business trips).
10. `response` node generates the final recommendation text.
11. `profile` node implicitly updates the user profile (e.g., adds "Travel types: business").
12. UI renders the chat response and the updated sidebar profile.

### Communication Style
1. **[context]** Context window assembled.
2. User types: "Please talk to me in casual tone."
3. `router` node identifies intent as "com_style" — bypasses the search pipeline entirely.
4. `profile` node implicitly updates the user profile (e.g., adds "Communication style: casual").
5. `response` node renders the acknowledgement in a casual tone.
6. UI renders the response and the updated sidebar profile.

### Returning User (Skip-Scoping Synergy)
This flow demonstrates the synergy between guided narrowing and persistent memory.
1. **[context]** Context window assembled. Profile already contains `preferred_brand = "Apple"` and `interests = ["Smartphones"]` from a previous session.
2. User types: "What about a tablet?"
3. `router` node identifies intent as "digital".
4. `scoping` node checks profile — `preferred_brand` is already set, so scoping is **skipped**.
5. `search` node directly fetches Apple tablets.
6. `guardrail` node filters for relevance.
7. `response` node generates the recommendation, shaped by the profile's communication style.
8. `profile` node implicitly updates the profile (e.g., adds "Interests: Tablets").
9. UI renders the response and the updated sidebar profile — **without ever showing a brand-selection button**.

## Key Product Concepts to Implement
- **Quick-Tap buttons:** These are NOT generated by the LLM. They are pre-defined in the `scoping` node based on the intent.
- **Implicit Memory:** The UI should show a "User Profile" sidebar that updates silently. Never output text saying "I have updated your profile." Just show the data changing in the UI.
- **Harness Engineering:** The context window passed to the "LLM" should only contain the user profile, a summary, and the last 3 conversations.
- **Skip-Scoping:** The `scoping` node must check the profile first. If enough is known, skip scoping and go straight to search. This is what makes the assistant feel like it "remembers" the user.
- **Multi-Round Scoping:** The Travel flow requires two scoping rounds (buttons -> text fields). The state tracks the round number.
